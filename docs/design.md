# 设计文档

## 1. 目标与边界

### 目标

为多个 LLM 上游提供统一入口，完成以下最小闭环：

1. 管理员配置上游渠道和下游 API Key。
2. 调用方使用统一地址和下游 Key 发起请求。
3. 网关完成认证、路由、转发和故障切换。
4. 网关记录请求结果和 token 用量。
5. 成功调用扣减下游 Key 配额。

### 不在当前版本内

- 用户登录和管理员权限系统。
- 跨实例分布式限流。
- 真正的流式 SSE 转发。
- 精确 token 计费和价格配置。
- 请求缓存和消息队列削峰。

## 2. 模块划分

| 模块 | 职责 | 不负责 |
|---|---|---|
| Channel | 上游渠道 CRUD 和状态管理 | 请求路由和转发 |
| ApiKey | 下游 Key 创建、哈希、状态和配额 | 上游调用 |
| Gateway | 认证、转发、故障切换、结果返回 | 渠道和 Key 的管理 |
| Routing | 模型筛选、权重选主、备用顺序 | HTTP 调用和日志 |
| RequestLog | 记录一次上游尝试的结果 | 修改路由决策 |
| MockLLM | 本地模拟上游，用于演示和测试 | 生产功能 |

## 3. 请求流程

```text
GatewayController
  -> GatewayService.forwardChatCompletion
  -> authenticate
  -> GatewayRoutingService.orderCandidates
  -> forwardToChannel
  -> createRequestLog
  -> upstream HTTP request
  -> updateRequestLog
  -> consumeQuota
```

`GatewayService` 在一次请求中只认证一次。路由会返回按优先级排好的候选渠道，当前渠道失败后继续尝试下一条。

## 4. 路由策略

### 模型筛选

请求中的 `model` 用于筛选渠道。没有支持该模型的渠道时返回 `400`，避免把请求错误地发到不兼容的上游。

### 权重选主

服务读取所有 `ENABLED` 渠道，把权重展开为一个逻辑槽位。请求按轮询序号落在槽位上：

```text
渠道 A 权重 1
渠道 B 权重 3

主渠道序列：A, B, B, B, A, B, B, B, ...
```

这样权重较高的渠道获得更多主请求。

### 故障切换顺序

主渠道排第一，其余渠道按权重降序、ID 升序排列。以下情况触发切换：

- 连接失败或请求超时。
- HTTP `408`。
- HTTP `429`。
- HTTP `5xx`。

HTTP `4xx` 通常表示请求本身有问题，继续换渠道不会解决问题，因此直接返回。

### 当前限制

轮询序号保存在单个 JVM 的 `AtomicInteger` 中。多实例部署后每个实例各有一套计数，权重分配仍可能存在偏差。生产环境可以把计数和渠道健康度放入 Redis，或者使用网关层的统一负载均衡策略。

## 5. 配额与并发

认证阶段先检查状态、过期时间和已用额度。成功返回后执行原子 SQL：

```sql
UPDATE downstream_api_key
SET used_amount = used_amount + 1
WHERE id = ?
  AND status = 'ACTIVE'
  AND (quota_amount = 0 OR used_amount < quota_amount)
```

判断和递增在同一条 SQL 中完成，避免两个请求同时读到相同旧值后把额度扣超。

当前版本在调用上游成功后才扣配额。如果两个请求几乎同时到达，并且只剩一个额度，它们可能都已经向上游发出请求，但最终只有一个请求能够成功扣减。要做到发送前严格预留，需要先写预占记录，再在上游失败时回滚。

### 速率限制

鉴权通过后，网关按下游 Key 执行固定窗口速率限制。默认每分钟 60 次，窗口内超过限制直接返回 `429`，不会选择渠道或调用上游。

当前计数保存在单机内存中。多实例部署后每个实例独立计数，需要迁移到 Redis 才能保证全局一致。

## 6. 数据一致性

### 已实现

- 一个请求的一次上游尝试对应一条 `request_log`。
- 渠道切换时会产生多条失败记录和一条成功记录。
- 下游 Key 只保存哈希，创建响应只返回一次完整 Key。

### 尚未解决

- 上游请求成功、日志更新失败时，会留下不完整日志。
- 扣减配额失败时，上游已经完成调用。
- 应用在上游返回前崩溃时，日志可能停留在 `PENDING`。

这些场景需要请求状态机、补偿任务或本地消息表，不应在两周 MVP 中伪装成已经完全解决。

## 7. 关键取舍

### 为什么使用 MySQL

题目允许 MySQL。当前数据具有较强的结构化关系，渠道、Key 和日志都适合持久化到关系型数据库，团队对 MySQL 也更熟悉。

### 为什么不在网关内直接升级为微服务

当前瓶颈主要是同步 HTTP 调用和数据库写入。先证明主链路和失败语义，再根据负载拆分，比提前引入消息队列和多个服务更容易解释和验证。

### 为什么先实现非流式

非流式转发更容易定义成功、失败和重试边界。流式请求一旦开始输出 token，就不能简单重试，需要处理“上游中途断开”“下游已收到部分内容”“是否可以续传”等问题。

## 8. 面试追问准备

### 上游吐了一半 token 才挂怎么办

当前版本不支持流式，因此不会出现半次返回。未来接入 SSE 后，需要区分：

- 尚未输出首 token：可以切换上游重试。
- 已经输出部分 token：不能无感重试，否则下游会收到重复内容。
- 可选方案：返回明确错误、使用可恢复会话、或者在首 token 前完成所有路由和限流检查。

### 两个请求同时抢最后一个额度

依赖原子 SQL 保证只有一个请求能把 `used_amount` 从剩余额度加满；另一个更新影响 0 行并返回 `429`。严格业务下应在发送上游前预占额度，并增加超时回滚。

### 多实例部署后权重还准吗

当前内存计数器不准。需要把计数或选主逻辑放到 Redis、数据库或统一网关层。

### 先记账还是先转发

当前先转发、成功后记账，优点是失败不扣费，缺点是无法严格阻止并发超发。更严格的方案是先预占额度，再转发，成功后确认，失败或超时后释放预占。

### 瓶颈在哪里

当前单实例的主要瓶颈是：

1. 每个请求至少一次同步上游调用。
2. 每次尝试至少两次日志数据库写入。
3. 单机 HTTP 客户端连接池和线程等待。

流量增长后优先考虑异步日志、连接池调优、批量写入和缓存渠道配置，而不是先拆微服务。
